# AGENTS

## Mission

Build `ARIEC61850` as a clean-room, reusable IEC 61850 native stack and a family
of tester applications on top of it.

The stack is the asset. Tester apps are replaceable clients of the stack.

Target capabilities:

- MMS client.
- MMS server and IED simulator.
- GOOSE publisher/subscriber.
- Sampled Values publisher/subscriber.
- SCL-driven station validation.
- WPF and CLI tester workflows for commissioning, troubleshooting, and lab use.

## Senior Engineering Posture

Work like this is protocol engineering, not demo coding.

- Prefer small byte-accurate modules over broad clever abstractions.
- Keep protocol code deterministic and testable without hardware.
- Make all uncertainty visible in names, diagnostics, tests, and docs.
- Separate parsing, modeling, runtime state, transport IO, and UI.
- Do not create code that only the original author can safely change.

- TestKit may depend on stack internals only when explicitly justified.
- Do not duplicate protocol logic in apps.

## Architecture Rules

### Codecs

Codec code reads and writes bytes only.

- Use `ReadOnlySpan<byte>`, `ReadOnlyMemory<byte>`, and big-endian primitives.
- Avoid string manipulation for binary protocol structure.
- Parser APIs should return typed objects plus enough raw evidence for
  diagnostics.
- Encoder APIs should be deterministic for the same input.
- Every encoder gets a matching parser or golden byte test.
- Every parser gets malformed input tests.
- Do not add network IO to codecs.

### Runtime Services

Runtime services manage state machines and clocks.

- Inject clocks.
- Inject transports.
- Expose trace events.
- Support cancellation and timeout.
- Keep state transitions explicit and testable.
- Never call UI code from runtime services.

### Transports

Transport adapters move bytes.

- In-memory transport comes first.
- PCAP replay transport comes before live NIC workflows when practical.
- Npcap/raw Ethernet transport must be in a separate project.
- Active publish APIs must require explicit adapter identity.

### Apps

Apps orchestrate workflows and present evidence.

- Apps do not parse BER, MMS, GOOSE, SV, or SCL directly.
- Apps call stack services and bind typed view models.
- Apps may add product-specific language, reports, and workflows.
- Apps must preserve stack diagnostics rather than flattening them into vague
  messages.

## Protocol Rules

### BER and MMS Data

- Support definite length only unless a real standard-mapped need requires more.
- Reject invalid long-form length and unsupported high-tag-number encodings
  until deliberately implemented.
- Preserve unknown MMS data tags as raw values.
- Do not silently coerce unknown values into strings.
- UTC time must carry quality byte.
- Floating-point encoding must have tests for MMS 5-byte format.

### GOOSE

Publisher must control:

- APPID.
- destination MAC.
- source MAC.
- VLAN ID and priority.
- `goCbRef`.
- `datSet`.
- `goID`.
- `t`.
- `stNum`.
- `sqNum`.
- `test`.
- `confRev`.
- `ndsCom`.
- `numDatSetEntries`.
- typed `allData`.

Rules:

- `stNum` increments only on state change.
- `sqNum` resets on state change and increments on retransmit.
- TimeAllowedToLive supervision belongs in subscriber runtime.
- SCL DataSet order is the semantic order when SCL exists.
- Without SCL, values are typed but semantically anonymous.
- Publisher retransmission schedule must be deterministic and testable.

### Sampled Values

Publisher must control:

- APPID.
- destination MAC.
- source MAC.
- VLAN ID and priority.
- `svID` or `smvID`.
- DataSet reference.
- `smpCnt`.
- `confRev`.
- `refrTm` when supplied.
- `smpSynch`.
- `smpRate`.
- `smpMod`.
- nofASDU.
- raw sample payload or typed payload mapping.

Rules:

- `smpCnt` wrap behavior must be explicit and tested.
- Do not assume one global channel order.
- DataSet entry order comes from SCL when available.
- Generic lab profiles may exist only as labeled profiles.
- Publishing at real SV rates requires a pacing service and performance tests.
- Software timing must not be described as measurement-grade.

### SCL

SCL is the engineering source of truth.

Parser must support:

- SCD, CID, ICD, IID, and XML SCL exports.
- IEC 61850-6 namespace variations.
- Header metadata.
- IED, AccessPoint, LDevice, LN0, LN.
- DataSet and FCDA order.
- GSEControl.
- SampledValueControl.
- ReportControl.
- Communication/GSE and Communication/SMV addresses.
- DataTypeTemplates with CDC, bType, enum type, and type id resolution.

Rules:

- Preserve order.
- Keep parse warnings.
- Support multiple files in one context.
- Show conflicts instead of choosing silently.
- Never silently correct semantic mapping.

### MMS Transport and Services

Build MMS in strict layers:

1. TPKT.
2. COTP.
3. ISO Session.
4. ISO Presentation.
5. ACSE.
6. MMS.

Rules:

- Do not skip handshake layers for a fast demo.
- Every layer has encode/decode tests.
- Association diagnostics must expose negotiated parameters.
- MMS client discovery is read-only first.
- Write/control workflows require explicit API and UI confirmation.
- Reports require a real ReportControl state machine.
- MMS server simulation must be SCL-backed and deterministic.

## UX Rules for Tester Apps

Taste-skill note: the frontend taste skill is mainly for landing pages, not
dense engineering dashboards. For this project, use its anti-slop principles:
clear hierarchy, honest state, readable density, contrast, and no decorative
noise.

Design read:

```text
Dense regulated engineering workbench for commissioning engineers, with calm
industrial cockpit UX, high evidence density, stable navigation, and direct
operator control.
```

General UX:

- The first screen is the actual tool, not marketing.
- Use stable left navigation for workspaces and targets.
- Use center tables/instruments for primary decisions.
- Use right inspectors for selected-target evidence.
- Put run/stop/adapter/session controls in predictable header positions.
- Do not use nested cards.
- Do not use decorative gradients, blobs, or purely ornamental visuals.
- Do not show generic warnings. Every warning needs a target.
- Do not reorder live targets by last seen, severity, or packet count unless the
  user explicitly selects that sort mode.
- Do not hide critical evidence behind ellipsis without a visible detail panel.

Expected WPF workspaces:

- Station.
- MMS Client.
- MMS Server.
- GOOSE.
- Sampled Values.
- Capture.
- Reports.
- Settings.

State model:

- `PASS`: verified and current.
- `WARNING`: usable but needs attention.
- `FAIL`: broken, mismatched, or unsafe.
- `UNKNOWN`: not enough evidence.
- `MATCHED`: live object matches SCL expectation.
- `WEAK`: partial match with missing confidence.
- `MISSING`: expected object not observed.
- `UNEXPECTED`: live object not explained by SCL.
- `MISMATCH`: observed field contradicts SCL.
- `CONFLICT`: multiple SCL/live candidates compete.

WPF layout:

- Inspect global styles before changing DataGrid layouts.
- Engineering grids with evidence need readable row heights.
- Raw packet grids may be compact.
- Long evidence belongs in an inspector/detail panel.
- Verify at 1600x900 and 1920x1080.
- Avoid monospace except raw IDs, hex, and protocol traces.

## Testing Rules

Before completing protocol work, run:

```powershell
dotnet test ARIEC61850.slnx
dotnet build ARIEC61850.slnx -c Release
```

Minimum tests for new protocol code:

- happy path decode,
- happy path encode,
- encode/decode round-trip,
- malformed length or missing field,
- boundary values,
- documented unsupported case.

Golden byte tests are preferred for:

- BER lengths,
- GOOSE APDUs,
- SV APDUs,
- TPKT/COTP/session/presentation/ACSE/MMS handshakes,
- report PDUs.

Do not delete tests to make a build pass.

## Documentation Rules

Update docs when behavior or boundaries change.

Required docs:

- `README.md`: current scope and how to build/test.
- `ROADMAP.md`: staged direction and next patch order.
- `AGENTS.md`: engineering rules.
- `docs/architecture/`: architecture decisions once modules split.
- `docs/validation/`: validation notes, lab captures, limitations.

Use precise language:

- Say "screening-level" when timing depends on software timestamps.
- Say "interoperability tested with X" only when evidence exists.
- Say "conformance" only after a formal conformance path exists.
- Say "clean-room" only when no copied implementation code was used.

## Do Not Do

- Do not mix tester UI logic into stack code.
- Do not mix active publishing into DigSubAnalyzer.
- Do not add network publishing before in-memory tests.
- Do not make a WPF screen before the stack API it needs is stable.
- Do not assume all vendors model SCL identically.
- Do not assume SV channel order without SCL evidence.
- Do not claim hardware timing precision from normal Windows/Npcap timestamps.
- Do not make a StationScout/IEDScout/SVScout clone. Build our own tool for the
  same engineering jobs.
